代理明明开着，
Antigravity 却报 400

一次真实的 Windows 排查记录：Electron 主进程、Go 语言服务器、子进程和回环请求，各自走了不同的路。最后用「全局 TUN 虚拟网卡 + 修复回环」把登录失败、400 和 ERR_TIMED_OUT 一起解决。

PUBLISHED2026-10-22 READ约 16 分钟 STACKAntigravity 2.25.0 · Electron · Go

TL;DR

  • 现象：系统代理（127.0.0.1:7892）开着，浏览器和 curl 都能出网；Antigravity 却登录失败、报 400，Go 语言服务器日志是 dial tcp ... connectex 超时，Electron 报 127.0.0.1:3313 ERR_TIMED_OUT。
  • 根因：系统代理只覆盖「愿意读 WinINET 的进程」。Go 语言服务器、Electron 的部分流量、GUI 启动的子进程不读系统代理，直连被丢；OAuth token 或 Code Assist 初始化只要有一条走直连，整个 IDE 就表现为 400 不可用。
  • 解法：代理客户端开全局 TUN，让流量在虚拟网卡层被接管；再把 localhost / 私网规则、DNS fake-ip、UWP 回环三个例外补上。账号地区不符合的报错是另一回事，TUN 解决不了。

01引言：代理开着，却报 400#

先给出结论：这次 400 既不是 Antigravity（Google 的反重力 IDE）的登录接口坏了，也不是代理节点挂了。代理确实开着，浏览器也确实能出网，但系统里还有一部分流量根本没经过代理。

现象很有欺骗性：Antigravity 2.25.0 打开后登录一直转圈，反复失败，界面最终报 400；重登、换节点、重装，都没能稳定解决。与此同时，浏览器正常，手动执行的 curl 请求也能返回代理出口。看上去网络完全没问题，只有这个 IDE 在「抽风」。

真正让排查转向的是日志。Go 语言服务器和 Electron 主进程分别留下了两类完全不同的错误：一类是公网 TCP 连接超时，另一类是本地 127.0.0.1 回环超时。两类错误同时出现，说明问题至少有两层：出网链路漏了一部分流量，本地服务又被回环问题补了一刀。

本文按「先证明有漏网流量 → 换一层接管方式 → 再补回环例外」的顺序复盘。它不只是一次换节点的过程，而是把 Windows 上「应用层代理」和「网卡层接管」的边界讲清楚。

排查原则

先证明「哪一条出网路径」失败，再谈换节点、重装或清缓存。界面上的 400 只是结果，不等于根因就在某个返回 400 的请求上。

02复现与日志证据#

先把环境钉死，避免把问题归咎于「网络环境不一样」：

  • 客户端Antigravity 2.25.0，Electron 桌面端 + 内置 Go 语言服务器
  • 系统Windows，命令统一使用 PowerShell
  • 代理系统代理开启，地址 127.0.0.1:7892；浏览器与手动 curl 可正常出网
  • 后续方案使用「龙猫云_Lite」（Clash 系内核）开启全局 TUN 虚拟网卡

登录失败时，语言服务器日志反复出现这段错误。注意它是 Go 风格的错误：dial tcp 表示在 TCP 连接阶段就失败了，connectex 是 Windows 上的连接 API。

language server · stderr
Post "https://oauth2.googleapis.com/token": dial tcp 108.177.125.95:443: connectex: A connection attempt failed because the connected party did not properly respond after a period of time

同一时段，Code Assist 的初始化请求也没有返回，端点同样是超时：https://daily-cloudcode-pa.googleapis.com/v1internal:loadCodeAssist。这两个请求一个负责换 OAuth token，一个负责初始化 Code Assist 会话，都不是可选项。

规律其实很清楚：浏览器这类会读取 WinINET 系统代理设置的进程都能正常出网；不读系统代理、也没有代理环境变量的进程，就会直连并超时。日志里的 dial tcp 正好落在这个分界线上。

另一边，Electron 主进程的日志是另一种错误：

electron · main process
Failed to load URL: https://127.0.0.1:3313/ with error: ERR_TIMED_OUT

两类错误，两个层面

  • 公网超时：目标 108.177.125.95:443 是日志里实际连接的 Google 地址。连接没有建立，说明这个进程尝试的是直连，并没有使用系统代理。
  • 回环超时：127.0.0.1:3313 是本地语言服务器提供的地址。它超时意味着 Electron 加载本地服务失败，可能是语言服务器还没就绪，也可能是回环请求被代理规则或 DNS 接管了。
  • 400 只是表象：登录流程需要先拿 token、再初始化 Code Assist；其中任意一步超时，客户端拿不到可用会话，最终只能把失败显示成 400 / 无法登录 / 无法拉取模型。

关键证据

浏览器和手动 curl 能出网，只证明「代理服务本身可用」，不能证明「系统里的每个进程都能走代理」。curl 的代理通常来自环境变量或 --proxy 参数，并不是 WinINET。日志里出现 dial tcp，说明发起请求的进程绕开了代理。

03拆解：到底漏了哪些流量#

Windows 的「系统代理」本质上是写在 WinINET / IE 设置里的一份注册表配置。它告诉应用「可以走 127.0.0.1:7892」，但是否遵守，由应用自己决定。于是同一个 IDE 进程组里，会出现多条互不相同的出网路径。

1. Go 语言服务器：只认环境变量，不认 WinINET

Antigravity 内置的 Go 语言服务器是一个独立进程。Go 标准库的 net/http 在默认 transport 下通过 ProxyFromEnvironment 取代理配置，也就是只读 HTTP_PROXY / HTTPS_PROXY 这类环境变量（以及小写形式），不会去读 Windows 的 WinINET 系统代理设置。

从 Explorer 双击启动的 GUI 进程，环境变量通常不包含代理配置；语言服务器作为子进程继承到的是「没有代理变量」的环境。于是它构造出的 TCP 连接是直连的，失败点正好对应日志里的 dial tcp 108.177.125.95:443。这也解释了为什么同一个应用「有时在终端里启动就正常」：终端会话里可能有代理环境变量。

2. Electron / Chromium：主体走系统代理，但存在旁路

Chromium 的大多数请求会读取系统代理，所以界面本身看起来能联网；但它并不是「所有字节都走同一条路」。本次需要重点怀疑的旁路包括：

  • QUIC / HTTP3：UDP 流量和 TCP 代理路径不同，部分场景下不会按 HTTP 代理规则走。
  • 自动更新与独立更新器：使用自己的网络栈，未必继承应用层代理设置。
  • 内置浏览器 / 登录回调：内嵌页面、localhost 回调、部分 IPC 请求可能走不同路径。
  • localhost 请求：回环地址可能被应用或代理规则特殊处理，出问题时的表现就是 ERR_TIMED_OUT。

3. 子进程与外部工具：不继承「系统代理」这个概念

应用调用外部系统工具时，比如 wsl.exe、git、node、语言服务器、更新器，子进程继承的是环境变量，而不是注册表里的 WinINET 设置。「系统代理」只是当前用户的一份 GUI 配置，并不会自动注入每个进程。

如果这些变量没设置，子进程就会直连；直连被阻断，表现出来就是超时、登录失败，或者只显示一个笼统的 400。应用本身可能完全不知道子进程没走代理。

4. 结论：一个漏点，整条链路失败

系统代理只覆盖「遵守它的应用」。剩下所有进程级直连都是漏网之鱼。只要 OAuth token 获取、Code Assist 初始化这些关键请求中有一条走了直连，端到端会话就建立不起来，整个 IDE 就会表现为 400 不可用。

04为什么系统代理救不了它#

要理解这个坑，得区分三种「代理接管」的层级。它们的覆盖范围完全不同，而系统代理是其中最弱的一种。

三种接管方式：谁会被覆盖，谁会漏掉
层级依赖什么覆盖谁典型漏网
系统代理
WinINET / 注册表		 应用主动读取当前用户的 IE / WinINET 设置 浏览器、部分 Electron / .NET 应用等「愿意配合」的进程 Go 语言服务器、子进程、独立更新器、QUIC 等
环境变量
HTTP_PROXY 等		 进程主动读取并遵循环境变量；子进程继承父进程环境 Go net/http、curl、git、部分 node 工具等 从 Explorer 启动的 GUI 进程、没设置变量的子进程
TUN 虚拟网卡
内核路由		 虚拟网卡 + 默认路由 + 代理客户端接管 几乎所有 IP 流量，包括不读任何代理设置的程序 回环 / 私网需显式例外；UWP 回环隔离另算

系统代理的第一个问题是「自愿协议」：应用可以不读。第二个问题是「不在进程环境里」：它存在于注册表，不会因为子进程被创建就自动出现在环境变量中。第三个问题是「木桶效应」：端到端流程里只要一个关键请求失败，页面就会报错，而你很难从界面看出是哪个进程挂了。

所以，继续在系统代理里换节点、调规则，本质上还是在赌「所有关键请求都愿意读这份配置」。而日志已经证明，至少有一个关键请求没有。

换个角度看

系统代理像在路口竖了一块「请走这边」的牌子；TUN 则是直接把默认路由改到虚拟网卡。前者依赖每个应用自觉，后者不再给应用选择。

05解法一：开全局 TUN，让网卡接管流量#

TUN 模式会在系统里创建一块虚拟网卡，把默认路由指过去。这样不管进程读不读 WinINET、有没有环境变量，它的 IP 流量都会先进入代理客户端，再由客户端按规则转发。它解决的不是「代理节点不好」，而是「有些进程根本没把流量交给代理」。

操作路径（本次环境）

  1. 确认客户端支持 TUN / 虚拟网卡

    本次使用的是「龙猫云_Lite」，Clash 系内核。不同客户端菜单文字不完全一样，找「虚拟网卡」「TUN 模式」这类入口即可。

  2. 打开开关：工具 → 进阶配置 → 网络 → 虚拟网卡

    开启后，客户端会请求创建虚拟网卡并修改路由。这一步需要管理员权限，普通用户无法创建网卡、写默认路由。

  3. 同意 UAC，让 helper 服务安装并启动

    本次同意 UAC 后，客户端安装了 lmclientHelperService，并设置为自动启动。这个辅助服务负责这些需要管理员权限的操作；拒绝 UAC 通常会导致 TUN 启动失败，或者只改了一半配置。

  4. 确认 helper 服务在运行

    如果客户端显示已开启但网卡没出现，先查服务状态：

    PowerShell · 检查 helper 服务
    Get-Service lmclientHelperService | Format-List Name, Status, StartType

    正常应看到 Status : Running，启动类型为自动。没有运行就先重启客户端；仍失败时再检查服务是否被安全软件拦截。

  5. 完全退出 Antigravity，再重新启动

    只关窗口不够。请从托盘退出，并在任务管理器里确认没有残留的 Electron 主进程、语言服务器或更新器进程。旧进程可能仍持有旧的连接和初始化状态；重启能让语言服务器重新建立会话。重启后先看 TUN 是否仍在工作，再打开 IDE。

  6. 系统代理要不要关？

    TUN 生效后，系统代理已不是必需品。两者同时开通常也能工作，客户端会自行处理；但排查阶段建议只保留 TUN，减少变量。如果出现异常，先关掉系统代理再测一次。

权限与安全

lmclientHelperService 是以管理员权限常驻的服务，能改网卡和路由。只应安装来自可信来源的客户端；排查结束或卸载客户端后，也确认服务是否被正确移除或停止。

TUN 开启后，原本走直连的 Go 语言服务器请求会进入虚拟网卡，OAuth token 和 Code Assist 初始化终于有了可用的出网路径。但「能出网」不等于「所有本地服务都正常」，回环问题会在第 7 节处理。

06怎么确认 TUN 真的生效#

不要只看客户端界面上的「已连接」。按下面五层依次验证：网卡是否存在、路由是否指过去、DNS 是否进入 fake-ip、绕过代理的请求是否仍从代理出口出去、原来失败的目标是否恢复。这五条互相独立，任何一条不过，都说明接管不完整。

检查 1 / 5：多出一块虚拟网卡

PowerShell · Get-NetAdapter
Get-NetAdapter |
  Where-Object Status -eq "Up" |
  Format-Table Name, InterfaceDescription, Status -AutoSize

期望看到一块新的网卡，例如 lmclient / lmclient Tunnel，状态为 Up。不同客户端命名不同，关键不是名字完全一致，而是「多了一块由代理客户端创建的虚拟网卡，并且处于 Up」。

检查 2 / 5：地址与默认路由都指向 TUN

PowerShell · 地址 + 默认路由
Get-NetIPAddress -AddressFamily IPv4 |
  Where-Object InterfaceAlias -like "lmclient*" |
  Format-Table InterfaceAlias, IPAddress, PrefixLength -AutoSize

Get-NetRoute -DestinationPrefix "0.0.0.0/0" |
  Format-Table InterfaceAlias, NextHop, RouteMetric, ifMetric -AutoSize

本次实测中，网卡地址为 198.18.0.1/30，属于 fake-ip 使用的地址段；默认路由 0.0.0.0/0 指向 lmclient Tunnel，metric 为 0。这说明系统默认流量会优先进入虚拟网卡——这是 TUN 生效最直接的证据，比客户端 UI 上的状态更可靠。如果你的网卡名不同，把命令里的 lmclient* 换成实际名称即可。

检查 3 / 5：DNS 解析进入 fake-ip 网段

PowerShell · Resolve-DnsName
Resolve-DnsName google.com -Type A |
  Select-Object Name, Type, IPAddress

本次环境启用了 fake-ip，解析结果应落在 198.18.x.x，而不是 Google 的真实 IP。fake-ip 让客户端能用「假地址」关联回真实域名，再按规则转发；如果你看到的是真实 IP，说明 fake-ip 没有生效，规则匹配行为会和预期不同。

检查 4 / 5：关掉 curl 自己的代理，仍然从代理出口出去

这是最关键的「反证」。curl.exe --noproxy "*" 明确告诉 curl：不要使用任何环境变量或代理配置，直接连。如果这样访问仍然返回代理出口的国家，就说明流量是在网卡层被拿走的，而不是靠应用配合。

PowerShell · 强制直连，验证 TUN 接管
curl.exe --noproxy "*" https://ipinfo.io/country

本次返回 TW，与代理出口一致。如果这条失败，前面的网卡和路由都白看了：可能是 helper 没运行、路由被别的 VPN 抢走，或 TUN 实际没有承接流量。反过来，如果这条成功，就证明「不读系统代理的进程」也能出网了。

检查 5 / 5：原来超时的目标恢复

PowerShell · Test-NetConnection
Test-NetConnection 108.177.125.95 -Port 443

这个 IP 来自语言服务器日志。TUN 生效前，这个 TCP 探测的结果是 TcpTestSucceeded : False；生效后应变为 True。Google 的 IP 会轮换，请优先使用当前日志里出现的 IP，不要把这个地址当成永久目标。

五条检查的因果关系

1–2 证明系统层接管，3 证明 DNS 进入接管范围，4 证明「不配合的进程」也能出网，5 证明原来的失败目标恢复。4 和 5 都通过，基本可以对公网连通性下结论了。

如果 TUN 生效，Antigravity 应该有什么变化

  • 登录流程可以走完，不再无限转圈或反复 400。
  • 语言服务器日志中不再出现 dial tcp ... connectex 超时，loadCodeAssist 能正常返回。
  • 模型列表可以拉取，能进入工作区。
  • 本地 127.0.0.1:3313 能正常加载（如果还不行，进入下一节）。

07解法二：把回环修好，别让本地请求也被「代」走#

TUN 解决了「漏流量」，却引出了第二个坑：回环。127.0.0.1 和 ::1 上的本地服务（Antigravity 语言服务器的 3313 / 3314，以及其他本地 API）在 TUN 接管全部路由后，可能因路由 / 劫持异常出现 ERR_TIMED_OUT，也可能被代理规则误匹配；此外，DNS 解析和 UWP 隔离也会造成类似的连接失败，表现为登录回调卡死。

先纠正一个误解

正常情况下，127.0.0.0/8 在系统里有本地路由，TUN 不会直接「抢走」回环流量。真正容易出问题的是 TUN 之后的代理规则、DNS fake-ip 和 UWP 回环隔离这三层。因此处理方式是补例外，而不是关掉 TUN。

7.1 代理规则排除回环与私网

让下列地址明确走 DIRECT，不要进入代理：

  • localhost、127.*、::1
  • 10.*（10.0.0.0/8）
  • 172.16.* – 172.31.*（172.16.0.0/12）
  • 192.168.*（192.168.0.0/16）

本次客户端在「排除域名」里配置了 localhost、127.*、192.168.* 等条目。如果你的客户端没有图形化的「排除域名 / bypass」列表，Clash 系配置的等价写法如下（字段名以实际客户端为准）：

Clash 系配置 · 等价写法
rules:
  - IP-CIDR,127.0.0.0/8,DIRECT,no-resolve
  - IP-CIDR,10.0.0.0/8,DIRECT,no-resolve
  - IP-CIDR,172.16.0.0/12,DIRECT,no-resolve
  - IP-CIDR,192.168.0.0/16,DIRECT,no-resolve
  - DOMAIN-SUFFIX,localhost,DIRECT

no-resolve 表示这条规则匹配时不为域名额外做 DNS 解析，可以避免本地名字被 fake-ip 污染。注意规则顺序：这些直连规则必须排在兜底的 MATCH / 代理规则之前。若配置来自订阅，手动改动可能被覆盖，优先使用客户端的「排除域名」入口。

7.2 DNS 劫持不要碰本地域名

TUN 的 DNS 劫持只应接管普通 DNS 查询，例如示例配置中的 any:53。与此同时，fake-ip-filter 里必须保留本地域名，例如 *.lan、localhost.ptlogin2.qq.com 这类需要解析到本机或局域网的名称。否则本地服务名会被分配一个 198.18.x.x 的假地址，连接自然到不了本地服务。

DNS / TUN 关键字段示意
dns:
  enable: true
  enhanced-mode: fake-ip
  fake-ip-filter:
    - "*.lan"
    - "localhost.ptlogin2.qq.com"

tun:
  enable: true
  dns-hijack:
    - "any:53"

这一段只展示关键字段，不同客户端可能使用不同键名或 GUI 开关。原则不变：本地域名必须绕过 fake-ip，否则本地服务会被当成远端域名处理。

7.3 UWP 应用的「回环隔离」

UWP / Microsoft Store 应用默认运行在 AppContainer 里，网络隔离策略默认禁止访问 127.0.0.1。当登录回调、WebView2 内嵌页或相关 Store 组件需要走 localhost 时，这个隔离会让请求直接失败，且看起来和网络超时非常像。需要显式把应用加入回环豁免名单。

本次使用的客户端目录里自带 EnableLoopback.exe，工具面板里也有「回环解锁工具」入口，可以直接用图形界面勾选需要访问 localhost 的应用。习惯命令行的话，可以用 CheckNetIsolation：

PowerShell · 查看 / 添加回环豁免
CheckNetIsolation LoopbackExempt -s
CheckNetIsolation LoopbackExempt -a -n="<PackageFamilyName>"

-s 列出当前豁免项，-a 添加。包名可以用 Get-AppxPackage 查询。先确认问题真的来自 UWP 隔离：纯桌面进程通常不受这条策略影响；它主要影响 UWP / Store 应用及其 AppContainer 组件。如果不确定客户端自带的回环解锁工具怎么用，优先用它，比手敲命令更不容易误操作。

修回环之前，先确认本地端口到底有没有在监听，这能把「语言服务器没启动」和「回环被劫持」区分开：

PowerShell · 看 3313 / 3314 是否在监听
Get-NetTCPConnection -LocalPort 3313,3314 -State Listen |
  Format-Table LocalAddress, LocalPort, OwningProcess -AutoSize

没有输出：语言服务器没有起来，优先检查公网初始化和进程状态。有 LISTENING 但仍然超时：更像回环规则、DNS 或 UWP 隔离的问题。

回环相关现象对照表
现象原因处理
Electron 报 https://127.0.0.1:3313/ ... ERR_TIMED_OUT，端口无监听 语言服务器没完成初始化，多半是它的公网请求被阻断 先修公网（开 TUN），完全退出后重启 IDE，再用 Get-NetTCPConnection 确认端口
端口有 LISTENING，但 localhost 请求仍超时 回环流量被代理规则误匹配，或本地域名被解析成 fake-ip 规则里把 127.0.0.0/8、::1 设为 DIRECT；检查 fake-ip-filter
登录回调页停在 localhost，页面空白或一直加载 回环回调被代理规则接管，或应用容器被禁止访问 loopback 排除 localhost / 127.*；使用「回环解锁工具」或 CheckNetIsolation

只在必要时使用的补充手段

如果你不想开 TUN，或者只想先救语言服务器，也可以给它显式设置环境变量：

PowerShell · 仅作为兜底方案
setx HTTPS_PROXY "http://127.0.0.1:7892"
setx HTTP_PROXY "http://127.0.0.1:7892"
setx NO_PROXY "localhost,127.0.0.1,::1"

setx 只影响之后新启动的进程，已经运行的应用必须重启；在 Windows 上通常还要重启 Explorer 或重新登录一次，新的 GUI 进程才会拿到变量。而且它只对「会读环境变量」的进程有效，管不到 Electron 的旁路流量或 QUIC。也可以使用支持 SOCKS5 注入的工具给指定进程注入代理，但那仍然是一个进程一个进程地补。想从根上少一个漏点，TUN 仍是更彻底的做法。

08排查流程图：从 400 到恢复#

把前面的判断整理成一条执行顺序。每一步都先用证据确认，再进入下一步，避免「换节点 → 重装 → 换客户端」的随机尝试。

1
日志里有没有 dial tcp ... connectex 或其他公网连接超时？

先看语言服务器日志，再看 Electron 主进程日志。不要从界面的 400 开始猜响应体。

没有 → 网络大概率不是根因：先查账号地区、登录态和客户端版本（见第 9 节） 有 → 进入第 2 步
2
用 curl.exe --noproxy "*" 强制直连，能通吗？

系统代理开着但强制直连失败，说明存在「不配合的进程」；这正是 TUN 要覆盖的场景。

能通 → 系统代理本身可用，问题可能只在特定进程：优先检查该进程的环境变量和日志 不通 → 开 TUN（第 5 节），再进入第 3 步
3
TUN 的五条检查是否全部通过？

网卡 Up、默认路由指向 TUN、DNS 返回 fake-ip、--noproxy 仍然从代理出口出去、原失败 IP 恢复。

任何一条不过 → 回到 helper 服务、UAC 权限、默认路由和客户端规则，TUN 还没真正接管 全部通过 → 公网链路基本修好，进入第 4 步
4
公网通了，但 127.0.0.1:3313 还超时？

用 Get-NetTCPConnection 看端口。没有监听说明语言服务器没起来；有监听则查回环规则、fake-ip 和 UWP 隔离（第 7 节）。

没有监听 → 完全退出 IDE 后重启，让语言服务器重新初始化；仍失败就看它的日志 有监听 → 修回环规则 / DNS / 回环解锁，然后重试登录
5
登录成功、模型列表能拉取了吗？

最后做验收：语言服务器不再出现超时，本地 URL 能正常加载，curl --noproxy "*" 仍返回代理出口。

是 → 收工，把「TUN + 回环例外」记入环境说明 否，但出现了 ineligible / not available in your location → 这是账号地区问题，转第 9 节，不要继续折腾 TUN

09边界与风险：TUN 不是万能钥匙#

9.1 TUN 会影响全局网络

TUN 改的是默认路由，影响的是整台机器，而不只是 Antigravity。开启前至少要意识到这些副作用：

  • 需要管理员权限：创建虚拟网卡和修改路由都不是普通用户权限，helper 服务会常驻。
  • 局域网可能受影响：NAS、打印机、开发板、内网系统如果没被规则排除，可能连不上。
  • 其他网络环境也会变：WSL 2、Docker、远程桌面、虚拟机网络都可能因默认路由改变而出现异常。
  • 规则错误会放大影响：排除列表写错时，可能不是「某个应用不能用」，而是「整台机器都不通」。
  • 不要叠加多个全局接管器：同时开两个 TUN 或多套 VPN，默认路由会互相抢，排查难度成倍上升。

建议在开启前后各保存一次路由快照，出问题时能快速对比：Get-NetRoute -DestinationPrefix "0.0.0.0/0"。停用 TUN 后也要检查默认路由是否回到原来的网关，避免残留路由造成「关了代理反而上不了网」。

9.2 公司内网 / VPN 环境要格外小心

公司 VPN 通常也会修改默认路由和 DNS，与 TUN 是直接竞争关系。两者同时开启时，可能出现「内网访问被送进代理」或「代理流量绕进公司 VPN」的情况，具体表现取决于两边的 split tunnel 配置。

在受管设备上，优先询问网络管理员，确认代理和 VPN 的使用边界；需要时把公司网段加入直连规则，或者只在处理 Antigravity 问题时临时开启 TUN，用完立即关闭。不要为了修一个 IDE 把公司内网路由搞穿。

9.3 账号地区限制：TUN 不等于解锁地区限制

如果 Antigravity 给出的提示是下面这种，而不是 400 / 超时，那它跟 TUN 基本无关：

地区限制提示（两种常见措辞）
Sorry, this account is ineligible to use Antigravity / not currently available in your location

这类提示来自 Google 账号关联的国家 / 地区，不是出口 IP 不够「干净」。判断依据是 Google 服务条款页面显示的国家；需要更改时，可通过 policies.google.com/country-association-form 提交申请。是否通过、何时生效，由 Google 决定，不是本地网络设置能解决的。TUN 只改变出口路径，不会改变账号的国家关联。

400 / 超时 vs. 地区不符：不要混为一谈
你看到的判断处理
界面报 400、登录转圈；日志有 dial tcp ... connectex、loadCodeAssist 超时、ERR_TIMED_OUT 网络链路 / 本地回环问题 全局 TUN + 回环例外；用第 6 节的五条检查确认
ineligible / not currently available in your location Google 账号关联地区问题 查看 Google 服务条款页国家，按官方流程申请更改关联；TUN 无效
网络日志干净，但只有地区提示 不是「漏流量」 不要再加代理规则；先确认账号资格与地区

别把两件事混成一件

看到 400 就开 TUN，可能只是碰巧遇到网络问题；看到地区提示还反复换节点、换 IP，则是在解决一个不属于网络层的问题。先分类，再动手。

10结语与一页速查表#

这次排查最有价值的不是「换成了 TUN」，而是把问题拆成了两个独立层次：出口链路和本地回环。系统代理是应用层的自愿协议，TUN 是内核层的强制改道；回环是改道之后必须手工留出的例外。理解这三句话，再遇到类似的「代理开着但某个 IDE 就是不行」，就不会从重装开始。

一句话记忆

系统代理只覆盖「愿意配合」的进程；TUN 取消了这个前提；回环是 TUN 之后必须补的例外；地区限制则完全是另一道题。

  • Antigravity 登录成功，模型列表可以拉取。
  • 语言服务器日志不再出现 dial tcp ... connectex 超时，loadCodeAssist 正常。
