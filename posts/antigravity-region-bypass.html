Antigravity 中国区账号复活实录

01

TL;DR（结论先行）

这起问题不是一道门，而是三道关。补丁只对第一关有效。

结论

要依次面对：① 客户端本地资格检查；② Google 账号验证；③ 请求来源 IP 的位置判定。本地二进制补丁只能过 ①；② 和 ③ 都在服务端，必须分别用「完成账号验证」和「支持地区的出口 IP」解决。

  • ① 本地

    补丁改的是 hasValidAuth。把判断改为无条件 true 后，客户端会跳过自己的资格检查，因此能进入主界面。它不会伪造服务端凭证，也不会改变服务端判定。

  • ② 账号

    账号验证要按服务端返回的流程完成。403 VALIDATION_REQUIRED 附带 validation_url，指向 Google 账号验证 / 条款确认。验证通过后，服务端记录验证态。

  • ③ 位置

    请求位置由来源 IP 决定。User location is not supported for the API use. 来自 Google 边缘节点的地区可用性判定，客户端补丁对此完全无效，只能更换出口 IP。

作者账号的注册地是中国，最终依然可用。关键不是「服务端不看账号国家」，而是：「账号国家 / 付款资料」与「单次请求的来源 IP 位置」是两套独立判定。前者主要影响付费档、订阅资格和企业归属；后者才决定这一次 API 请求是否放行。

因此，在这套判定模型下，只要 (a) 账号完成验证，并且 (b) 请求从支持地区的出口 IP 发出，中国注册的账号同样可用。这里说的是条件满足时的判定逻辑，并不代表任意时间、任意网络都能通过。

本地放行，不等于服务端放行。

02

问题现象

同一个「用不了」，在不同阶段对应不同错误。把报错原文留全，是这次能分清层级的前提。

  1. 打补丁前

    客户端的地区 / 资格检查直接拦住，无法进入主界面，只留下资格提示。

  2. 登录后

    能进入主界面，但模型额度（Model Quota）一直转圈，加载不出来。

  3. 会话发消息

    请求失败，报 Error: Verification Required。

  4. 进一步查看

    服务端返回 HTTP 400，响应体指出了另一层原因。

响应体原文http
HTTP 400
{"code":400,"status":"FAILED_PRECONDITION","message":"User location is not supported for the API use."}

不要合并处理

Verification Required 指向账号验证（②）；User location is not supported 指向请求位置（③）。它们可能在同一次排查中先后出现，但不是同一个错误的两种写法。

03

三道关卡的判定模型

排查的关键不是背错误码，而是先判断这一段逻辑由谁执行。按判定者拆分后，三道关的边界就清楚了。

三道关卡的判定者、典型错误以及本地补丁是否能解决
关卡 判定者 典型错误 本地补丁能解决吗
① 本地资格检查 客户端 language_server 自身 无法进入主界面 / 资格提示 能
② 账号验证 Google 账号侧（cloudcode-pa 后台） 403 VALIDATION_REQUIRED，附 validation_url 不能，但可手动完成验证
③ 请求位置 Google 边缘节点（响应头 Server: ESF）按来源 IP 400 FAILED_PRECONDITION: User location is not supported 不能，只能更换出口 IP

本地补丁之所以会带来「能进但不能用」的割裂感，就是因为它只覆盖了表格第一行。进入主界面属于客户端状态；额度能否加载、聊天能否完成，还需要服务端分别认可账号验证状态和请求来源位置。

证据

403 VALIDATION_REQUIRED 的响应体里带有 validation_url；400 FAILED_PRECONDITION 的响应头中可见 Server: ESF。一个指向账号侧流程，一个来自边缘节点。

04

作者的实际操作步骤

以下按实际操作顺序记录。每一步都注明它针对的层级；没有改变的层级，也会明说。

  1. 01
    步骤 1 目标 ① / 本地资格检查

    打本地补丁：把 hasValidAuth 改为无条件 true

    目标文件是安装目录下的 language_server.exe。示例路径如下，实际路径以本机安装目录为准：

    目标文件 / 示例路径path
    C:\Users\syste\AppData\Local\Programs\antigravity\resources\bin\language_server.exe

    原理：hasValidAuth 是客户端 language_server 内部的布尔标志。把它的判断改成无条件 true，客户端就会跳过本地资格检查，对自身资格「放行」。

    真实字节改动是等长 6 字节替换，文件大小不变：

    补丁前 / 补丁后x86-64
    补丁前  80 78 08 00  74 3b
          cmp byte ptr [rax+8], 0 ; je +0x3b

补丁后  c6 40 08 01  90 90
          mov byte ptr [rax+8], 1 ; nop ; nop

    完整上下文是一个 12 字节窗口，替换后其余字节保持不变：

    12 字节上下文bytes
    前：85 db 75 41 80 78 08 00 74 3b 48 8b
后：85 db 75 41 c6 40 08 01 90 90 48 8b

    本文记录时使用的是 2.25.0 构建，观察到的偏移为 0x2645E8A。这个数字只对当前样本有意义：不同版本的偏移会变，必须自己重新定位特征码，不要照抄偏移。

    操作前

    先完整备份原文件（例如 language_server.exe.agybak），并完全退出所有 Antigravity 进程（含 language_server）。文件被占用时无法写入；没有备份就无法回退。补丁是原地等长替换，只改 6 字节，不改变文件大小。

    这一步只解决 ①。补丁让客户端自认合格，但没有改变账号的验证状态，也没有改变请求的来源 IP。

  2. 02
    步骤 2 通过 ① / illegal 提示

    过掉登录时的 illegal 提示

    补丁后，用原账号登录。原本的地区 / 资格拦截（登录时的 illegal 提示）不再阻断，可以进入主界面。

    这个结果只证明第 ① 关被绕过；账号本身和网络位置没有被改变。

    状态变化：从「进不去主界面」变为「可以进入」，但还不能据此判断模型请求是否可用。

  3. 03
    步骤 3 目标 ② / 仍未通过

    这时仍然不可用

    进入主界面后，模型额度面板一直 spinner；在会话里发送消息也失败，报 Error: Verification Required。

    这说明第 ① 关已经不再是当前阻碍，但服务端的账号验证还没有完成。

    状态变化：本地入口恢复，模型额度和聊天请求仍被服务端拦下。

  4. 04
    步骤 4 触发 ② / 账号验证

    去会话里发一句「你好」

    在会话里发送一句「你好」。客户端请求 Cloud Code Assist 后端，服务端将请求拦下，并弹出「验证身份 / 账号信息」流程。

    这一次被拦下的不是本地资格，而是服务端要求的账号验证。日志里对应的关键错误是 403 VALIDATION_REQUIRED。

  5. 05
    步骤 5 解决 ② / 完成验证

    完成 Google 的验证

    按流程完成 Google 验证。日志中观察到的验证链接结构如下，参数已省略：

    验证链接结构 / 参数省略url
    https://accounts.google.com/v3/signin/continue?plt=...
&continue=https://developers.google.com/gemini-code-assist/auth/auth_success_gemini&...

    注意 continue 指向 gemini-code-assist 的 auth_success。这说明它是 Google 账号身份验证 / 条款确认，不是地区判定。

    不要把带 token 的原始链接发到任何地方。日志、截图和求助帖中只保留结构，删除查询参数。

  6. 06
    步骤 6 结果 / 恢复可用

    验证完成后恢复可用

    验证完成后，模型额度面板可以加载，聊天恢复正常。

    推断，未经实证

    记录到的恢复发生在验证完成之后，但这份日志无法单独把恢复归因于验证动作。也可能与当时请求的出口 IP 已落入支持地区有关，或者两者共同作用。详见 §5.5。

05

原理拆解

把操作和原理分开看，三条错误的边界会非常清楚：能改的是客户端状态，不能改的是服务端判定。

5.1补丁只改了客户端，改不了服务端

hasValidAuth 是客户端 language_server 内部的布尔标志。改成 true 只是让客户端「自认合格」，从而跳过本地检查。它不会向 Google 发送任何伪造凭证，也不会改变服务端的任何判定。

因此，「能进入主界面」和「能被服务端放行」是两个不同命题。前者是本地状态，后者需要服务端认可。

5.2403 VALIDATION_REQUIRED 到底要求什么

retrieveUserQuotaSummary 返回的 403 中，关键信息不是「地区不支持」，而是账号验证：

403 / 字段节选log
reason:                   VALIDATION_REQUIRED
domain:                   cloudcode-pa.googleapis.com
validation_error_message: "Verify your account to continue."
validation_url:           https://accounts.google.com/v3/signin/continue?plt=...
                          &continue=https://developers.google.com/gemini-code-assist/auth/auth_success_gemini&...

错误体里的 reason、domain 和 validation_error_message 都指向账号侧；validation_url 则给出完成验证的入口。链接的 continue 指向 gemini-code-assist 的 auth_success，这进一步说明它是账号身份验证 / 条款确认，不是网络地区判定。

结论：验证通过后，服务端记录验证态；后续 retrieveUserQuotaSummary 与聊天请求不再返回该错误。

证据

reason: VALIDATION_REQUIRED、domain: cloudcode-pa.googleapis.com、validation_error_message: "Verify your account to continue."，再加上指向 accounts.google.com 的 validation_url，共同构成账号验证要求。

5.3400 FAILED_PRECONDITION 才是真正的地区判定

User location is not supported for the API use. 是 Google 边缘节点按请求来源 IP 做出的地区可用性判定。响应头中可见 Server: ESF 与 X-Cloudaicompanion-Trace-Id。

这是 IP 层判定，客户端补丁完全无效。只改本地二进制不可能改变来源 IP，也不会让服务端换一个位置来看这次请求。

结论

User location is not supported 出现时，应该检查出口 IP，而不是继续在二进制里找开关。补丁无法改变网络路径，也无法改变边缘节点看到的来源位置。

5.4为什么「中国账号」也能通过——关键结论

很多误判来自把「账号注册地」当成「请求位置」。在这个案例里，它们是两套独立判定：

账号国家 / 付款资料与单次请求来源 IP 的独立判定关系
判定维度 账号国家 / 付款资料 单次请求来源 IP
依据 账号资料与付款资料 这一次请求的出口 IP 位置
主要影响 付费档、订阅资格、企业归属 本次 API 调用是否放行
本地补丁能否改变 否 否

因此，只要 (a) 账号完成验证，并且 (b) 请求从支持地区的出口 IP 发出，中国注册的账号同样可用。账号国家不决定这一次请求是否被边缘节点放行。

结论

账号国家 ≠ 请求来源位置。前者主要影响付费档、订阅资格与企业归属；后者按「这一次请求从哪里来」单独判定。两者不能互相替代。

5.5显式标注的不确定性

下面两条不能当作已证实结论。把它们与前面的日志事实分开看。

推断，未经实证

无法 100% 确认最终放行是仅因为「验证完成」，还是因为当时请求的出口 IP 已经落到支持地区，或两者都需要。日志中 403 与 400 先后出现，符合「先验证、再位置」的顺序，但这只是推断。

推断，未经实证

日志中出现过台湾数据中心 IP（169.128.55.233，AS1405 Caelus Technology LLC）被判定 location not supported 的记录。这说明「支持地区」不等于「任意该地区 IP 都可用」；机房 IP 可能被额外拒绝。

因此复现时不要只凭「已经验证」就断定一定能用，也不要仅凭 IP 归属地判断会被放行。② 和 ③ 需要分别验证。

07

可复现清单

把操作拆成可勾选的步骤。每一步都对应一个可验证的状态，避免「改完看起来没问题」。

  • 备份原二进制。
  • 完全退出所有 Antigravity 进程；在任务管理器确认没有 language_server 在运行。
  • 定位特征码后再改字节，不要照抄偏移。
  • 改完校验：文件大小不变、原特征码消失、新特征码出现。
  • 启动后先看模型额度是否能加载。
  • 若报 Verification Required：完成 Google 验证流程。
  • 若报 User location is not supported：更换出口 IP（住宅 IP 优先，机房 IP 容易被拒）。
  • 验证后仍失败则查看日志：%APPDATA%\Antigravity\logs\language_server.log。

如果 ① ② ③ 都排除后仍然失败，回到日志继续定位。不要为了「试出来」连续盲改字节或反复更换无关配置。

08

风险与边界

方法有明确边界。以下几条都不应该被忽略。

应用更新会覆盖补丁

应用每次自动更新都会覆盖 language_server.exe，补丁随之失效，需要重新打。更新还可能整体替换 resources\bin 目录，连备份一起清掉。

更新影响 / 示意tree
更新前
resources\bin\
├─ language_server.exe          ← 已打补丁
└─ language_server.exe.agybak   ← 备份

更新后（示意）
resources\bin\                  ← 目录被整体替换
├─ language_server.exe          ← 新版本，补丁消失
└─ language_server.exe.agybak   ← 备份也可能被清掉

备份最好放在安装目录之外，不要假设更新会保留它。

修改二进制违反应用服务条款

修改二进制文件违反应用服务条款，可能导致账号受限。是否承担这个风险，需要由操作者自行判断。

服务端判定随时可能变化

服务端判定随时可能变化，本方法不保证长期有效。这一次记录到的行为，不构成对后续版本或后续请求的保证。

不要泄露账号凭证与验证链接

不要在任何地方分享自己的账号凭证，也不要分享验证链接中的 token。验证链接可能携带一次性身份凭据，完整链接、截图和日志都可能泄露它。

警告

公开任何排查记录前，先删除 validation_url 的查询参数、cookie、Authorization 头以及可能出现的账号标识。

现象 层级 对策
进不去主界面 ① 本地检查 重新打补丁 / 确认版本偏移正确
